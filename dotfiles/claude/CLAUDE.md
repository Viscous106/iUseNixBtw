# Git — I handle all write operations myself
NEVER run git write/history-changing operations. This includes (not limited to):
`git add`, `commit`, `push`, `pull`, `merge`, `rebase`, `reset`, `revert`, `restore`,
`checkout`/`switch` (when they change files), `stash`, `tag`, `rm`, `mv`, `cherry-pick`,
`clean`, `apply`, and the same via any alias/wrapper (e.g. the `config`/dotfiles bare-repo
alias `git --git-dir=... --work-tree=...`), plus `gh pr create/merge`, `gh release`, etc.
Instead, do the file edits and then PRINT the exact command(s) for me to run myself,
in a copy-paste block. Read-only git is fine and encouraged: `status`, `diff`, `log`,
`show`, `ls-files`, `branch --list`, `remote -v`, `rev-parse`, `blame`.

# Git — we push straight to main, no branches or PRs
The commands I print are for committing on `main` and pushing to `origin main`. Do not suggest feature branches,
`git switch -c`, `gh pr create`, or "open a PR / claim an issue first" steps, and do not split work into one branch
per concern. Still keep commits small and one-concern so history reads well. If a push is rejected because the remote
moved, print `git pull --rebase --autostash` then `git push`. This overrides a project CLAUDE.md that asks for PRs.
Fact worth remembering: in mergit, a push to `main` that touches code runs CI and then auto-deploys to the server,
so mention it when a commit will trigger a deploy; that is information, not a reason to use a branch.
